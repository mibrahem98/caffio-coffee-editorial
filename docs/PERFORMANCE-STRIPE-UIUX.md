# تقرير الأداء وStripe وتحسينات UI/UX — Caffio Coffee

**تاريخ المراجعة:** 14 أغسطس 2026  
**نطاق هذا التقرير:** واجهة Caffio العامة، وأداء التحميل، ومحاكاة Caffio Society، وخطة الانتقال الآمن إلى اشتراك Stripe فعلي.

> **القاعدة التشغيلية الحالية:** لا يجمع الموقع رقم بطاقة أو عنوان شحن، ولا ينشئ دفعة أو شحنة أو اشتراكًا حقيقيًا. يظل Caffio Society محاكاة محلية إلى أن تُعتمد بنية Stripe والمفاتيح وقواعد التنفيذ.

## ملخص تنفيذي

تم تحويل تحميل صفحات Caffio من حزمة JavaScript واحدة كبيرة إلى حزم حسب المسار، مع إزالة عميل بيانات غير مستخدم من تحميل الواجهة العامة وتحديد أولوية صورة Hero وتأجيل الصور غير الأساسية. كما أضيفت اختبارات تمنع تراجع هذه التحسينات، مع مراجعة شاملة للمسارات وسجل المتصفح.

| المؤشر | قبل التحسين | بعد التحسين | الأثر العملي |
|---|---:|---:|---|
| JavaScript الرئيسي المضغوط | 237.54 كيلوبايت | لا توجد حزمة رئيسية واحدة؛ حُزم حسب المسار | لا تنتظر المتصفح كود صفحات المنتج والمجلة وSociety في الصفحة الأولى. |
| CSS المضغوط | 30.25 كيلوبايت | 30.39 كيلوبايت | تغير طفيف بسبب واجهة التحميل؛ لا يمثل عنق زجاجة رئيسيًا مقارنة بـ JavaScript. |
| الحمولة الأولية التقديرية للصفحة الرئيسية، مضغوطة | 267.79 كيلوبايت | 213.27 كيلوبايت | انخفاض **20.36%** في أصول البدء التقديرية، مع تأجيل كود المسارات المتخصصة. |
| اختبار الوحدة | 8 ناجحة | 8 ناجحة | منطق المحاكاة والسلة وحارس Stripe بقي سليمًا. |
| اختبار المتصفح | 19 ناجحًا + 1 متجاوز عمدًا للـ hover على اللمس | 21 ناجحًا + 1 متجاوز عمدًا | أضيفت تغطية للأداء والوصولية والمسارات. |

تُقاس الأرقام من مخرجات بناء الإنتاج، لا من سرعة شبكة حقيقية؛ لذلك يجب قراءة الانخفاض كمؤشر لحجم الأصول القابلة للنقل، لا كوعد بزمن LCP ثابت. تختلف السرعة الفعلية حسب اتصال الزائر، التخزين المؤقت، ومصدر الصور.

## ما الذي تغيّر في الأداء

### 1. تحميل الصفحات عند الحاجة

تُحمّل الصفحة الرئيسية أولًا، ثم تُجلب صفحات تفاصيل القهوة، المفضلة، التتبع، الملف المحلي، ملاحظات الحقل، دراسة الحالة، وCaffio Society عند فتح المسار المطلوب. هذا يحافظ على المسارات الحالية، لكنه يمنع إرسال منطق كل الصفحات للزائر الذي يريد الصفحة الأولى فقط.

ظهرت حزم مستقلة للصفحة الرئيسية والمنتج وSociety والمفضلة وغيرها، إلى جانب حزم مشتركة للإطار وواجهة الأيقونات. يوجد أيضًا Loader قصير باحترام `prefers-reduced-motion` لحالة الانتقال النادرة أثناء جلب مسار مؤجل.

### 2. إزالة تكلفة عميل بيانات غير مستخدم

كان مدخل الواجهة العامة يهيئ tRPC وReact Query حتى مع عدم وجود أي استعلام بيانات فعلي في مسارات Caffio العامة. أزيلت هذه التهيئة من العميل فقط، فيما بقيت البنية الخلفية كما هي للمستقبل. النتيجة هي عدم تحميل عميل بيانات ومفاتيح مصادقة لا تحتاجها تجربة Caffio الحالية.

> عند تنفيذ اشتراك حقيقي مستقبلًا، لا يعاد تفعيل عميل البيانات في كل الموقع تلقائيًا. الأفضل تحميله فقط داخل تدفق حساب/إدارة اشتراك محمي، أو إبقاء Checkout مستضافًا مع طلبات خادم محددة.

### 3. استراتيجية الصور

صورة Hero هي العنصر المرئي الأول؛ أصبحت ذات أولوية تحميل عالية مع فك ترميز غير متزامن. أما صور البطاقات والملاحظات والطقوس خارج شاشة البداية فتُحمّل كسولًا وتُفك شفرتها بصورة غير متزامنة. تقل هذه الاستراتيجية منافسة الصور الثانوية لعناصر البداية.

### 4. حواجز الجودة المضافة

اختبارات المتصفح تتحقق الآن من أن صورة Hero تحمل `fetchpriority="high"`، وأن الصور غير الأساسية تستخدم التحميل الكسول، وأن المسارات العامة الثمانية ترسم محتوى رئيسيًا، وأن رابط تخطي المحتوى يعمل بلوحة المفاتيح، وأن تباين الرأس يتغير بعد التمرير.

## ربط Stripe: الخطة الصحيحة والآمنة

### الوضع الحالي

حاول المشروع تفعيل Stripe Claimable Sandbox، لكن منطقة الحساب غير مؤهلة له. لا توجد مفاتيح Stripe صالحة في المشروع، ولذلك تمنع واجهة Society الإتمام الحقيقي وتعرض وصفًا صريحًا للمحاكاة. الحارس الحالي لا يعد المسار جاهزًا إلا إذا وُجد مفتاح خادم يبدأ بـ `sk_` ومفتاح واجهة يبدأ بـ `pk_`.

### المتطلبات قبل أي تطوير حي

| المتطلب | المسؤول | سبب الحاجة |
|---|---|---|
| حساب Stripe مؤهل ومفعّل | مالك العلامة | تحديد أهلية البلد والعملة والتحقق التجاري قبل قبول المال الحقيقي. |
| منتجات وأسعار دورية معتمدة | مالك العلامة + التشغيل | لا يجوز تخمين السعر أو الدورة أو الضريبة أو سياسة الإلغاء. |
| سياسة اشتراك وإلغاء وخصوصية وشحن | مالك العلامة + المستشار القانوني المناسب | تجعل شروط الاشتراك، المعالجة، والاسترداد قابلة للعرض والتنفيذ. |
| قرار التنفيذ والشحن | مالك العلامة | يلزم تأكيد منطقة الخدمة، الناقل، التكلفة، وإيقاع التحميص قبل إصدار اشتراك. |
| مفاتيح اختبار أولًا | مالك العلامة | تجريب التدفق دون تحصيل أموال حقيقية. |

### المفاتيح والمتغيرات المطلوبة

لا ترسل أي مفتاح داخل محادثة، أو بريد، أو ملف مصدر، أو مستودع Git. تُدخل المفاتيح من واجهة إدارة المشروع: **Settings → Payment**. يبدأ الاختبار بمفاتيح Sandbox/Test وينتقل إلى Live فقط بعد قائمة إطلاق مكتملة.

| المتغير | مكان الاستخدام | الحالة الأمنية |
|---|---|---|
| `STRIPE_SECRET_KEY` | الخادم فقط لإنشاء جلسات Checkout واسترجاع حالة الاشتراك. | سري؛ لا يصل إلى المتصفح. يفضل مفتاحًا مقيّدًا مناسب الصلاحيات عند الإمكان. |
| `VITE_STRIPE_PUBLISHABLE_KEY` | المتصفح فقط عند استخدام Stripe.js أو Payment Element. | قابل للعرض للعميل؛ ليس بديلًا عن سر الخادم. |
| `STRIPE_WEBHOOK_SECRET` | الخادم فقط للتحقق من توقيع كل webhook. | سري ومختلف عن مفتاح API. يوجد لكل endpoint. |
| `STRIPE_PRICE_<PLAN>` | الخادم فقط، مثل `STRIPE_PRICE_WEEKLY`. | يربط اختيار Society بسعر Stripe معتمد بدل تمرير مبلغ من المتصفح. |
| `STRIPE_SUCCESS_URL` و`STRIPE_CANCEL_URL` | الخادم/الإعدادات. | يحددان العودة بعد Checkout، لكنهما لا يثبتان نجاح الدفع. |

يوضح Stripe أن مفاتيح Test تبدأ مثل `pk_test_` و`sk_test_`، وأن Live تستخدم `pk_live_` و`sk_live_`. كما يوضح أن المفتاح القابل للنشر وحده مناسب للواجهة، فيما تحفظ مفاتيح الخادم في مخزن أسرار أو متغيرات خادم فقط [1].

### المسار المقترح: Stripe Checkout المستضاف

لأن Society اشتراك دوري، يبدأ التنفيذ المقترح بـ **Stripe Checkout المستضاف** بدل جمع أي بطاقة داخل Caffio. ينشئ خادم Caffio جلسة Checkout بوضع `subscription` مع `priceId` معروف للباقة، ويرسل المتصفح إلى Stripe. هكذا لا تتعامل واجهة Caffio مع رقم البطاقة أو CVC، ويبقى تخصيص الهوية في الصفحة القبلية وبعد العودة.

1. ينشئ المالك منتجات وPrices دورية في Stripe Dashboard، بناءً على دورات Society المعتمدة.
2. ينشئ الخادم جلسة Checkout من `priceId` محفوظ لديه، وليس من مبلغ يرسله المتصفح.
3. يمرر الخادم فقط اختيارات موثوقة ومصرحًا بها مثل القهوة والطحن والدورة، ويربطها بـ `metadata` منضبط.
4. يُعاد الزائر إلى `success_url` أو `cancel_url`، لكن صفحة النجاح تعرض حالة «قيد التأكيد» حتى يعالج الخادم webhook موثوقًا.
5. تحفظ قاعدة البيانات معرفات Stripe فقط، مثل `customerId` و`subscriptionId` و`priceId` و`status` ووقت آخر حدث؛ لا تحفظ بيانات البطاقة.
6. توفر بوابة حساب محمية لاحقًا لإدارة الإلغاء أو الإيقاف أو تحديث وسيلة الدفع عبر Stripe Customer Portal، وليس عبر واجهة محلية غير موثقة.

توثق Stripe إنشاء اشتراكات عبر Checkout، بما في ذلك خيار صفحة مستضافة أو مضمّنة أو نموذج مضمّن [2]. اختيار الصفحة المستضافة هو الأنسب كبداية لأنه يقلل نطاق التعامل مع بيانات الدفع داخل التطبيق.

### الويبهوكس: مصدر الحقيقة

العودة من Stripe إلى صفحة النجاح ليست إثباتًا كافيًا للدفع أو تفعيل الاشتراك. يجب أن يرسل Stripe webhook إلى endpoint HTTPS، ويجب على الخادم التحقق من التوقيع باستخدام **نص الطلب الخام** و`STRIPE_WEBHOOK_SECRET` قبل كتابة أي حالة اشتراك. توصي وثائق Stripe بالرد السريع بـ `2xx` قبل المنطق الطويل، وباختبار endpoint محليًا عبر Stripe CLI [3].

الحد الأدنى من الأحداث المقترحة:

| الحدث | الإجراء الخادمي |
|---|---|
| `checkout.session.completed` | ربط الجلسة بسجل المستخدم/المحاكاة وتسجيل معرف اشتراك Stripe. |
| `customer.subscription.created` و`customer.subscription.updated` | مزامنة الحالة، السعر، فترة الفوترة، وحالة الإلغاء. |
| `customer.subscription.deleted` | إيقاف التجديد في Caffio وعدم إنشاء تنفيذ جديد. |
| `invoice.paid` | تأكيد دورة مدفوعة عند الحاجة التشغيلية. |
| `invoice.payment_failed` | تسجيل الحالة وإظهار إرشاد آمن للمستخدم إلى بوابة Stripe بدل محاولة خصم محلي. |

يجب جعل معالجة الأحداث **idempotent**: يُخزن `event.id` بعد نجاح المعالجة كي لا يكرر webhook نفس الأثر. كما يجب التحقق من كل معرف في Stripe من الخادم بدل الثقة بـ metadata أو استعلامات المتصفح وحدها.

### خطة الاختبار قبل الإطلاق

1. إضافة مفاتيح Test في Settings → Payment فقط.
2. إنشاء بيئة Sandbox منفصلة عن Live وعدم مزج أسعارها أو مفاتيحها.
3. تجربة إكمال Checkout، الإلغاء، فشل الدفع، وتجديد الفاتورة باستخدام بيانات الاختبار الرسمية.
4. استخدام Stripe CLI لتمرير أحداث اختبار إلى endpoint المحلي/المعاينة والتحقق من التوقيع.
5. اختبار منع تكرار webhook، وتعطل endpoint مؤقتًا، وحالة عودة المستخدم قبل وصول webhook.
6. مراجعة السلة وSociety على الهاتف ولوحة المفاتيح، ثم إنشاء اختبارات Vitest وPlaywright لمسار النجاح والفشل.
7. فقط بعد اعتماد السياسة والتنفيذ والأسعار والضرائب، الانتقال إلى مفاتيح Live ومراجعة قائمة Stripe للإطلاق.
